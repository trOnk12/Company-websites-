## The problem

Puzzle 1 showed the next run matching each call to its group: by the call's key, and, for calls with the same key, by their order. An `if` keeps a group of its own, so nothing after it shifts. A list is different. A loop calls `PersonRow` once per person, always from the same line of code, so every row carries the same key and only order tells them apart. You type a note into Ben's row, kept with `remember`, and then a new person arrives at the top of the list. Whose row shows your note now?

## The building block

Android's docs say a composable's instance in the composition "is identified by its **call site**": the place in your source where the composable is called. Two different lines that call `Counter` are two call sites, told apart by their order (puzzle 1). A loop is one call site that runs many times:

```kotlin
Column {
    for (person in people) {
        PersonRow(person)          // one call site, one call per person
    }
}
```

Each `PersonRow` call opens a group with `PersonRow`'s key, and the slot table holds them one after another. On the next run, the first call takes the first group, the second call the second, and so on. Nothing ties a group to a person. The docs put it plainly: when calls come from the same call site, "the execution order is used in addition to the call site".

So when Zoe is inserted at the top, the first call (now Zoe) takes the group that held Ana, the second call (now Ana) takes the one that held Ben, with the note you typed, and so on. A new group is added at the end for the last person. Each row gets new arguments, so every row runs again, and any value it remembered now shows under someone else's name. Adding at the bottom is harmless: every old row keeps its position.

The fix is to give each call an identity of its own. **`key()`** is a composable that takes one or more values and wraps the calls inside it:

```kotlin
for (person in people) {
    key(person.id) {
        PersonRow(person)
    }
}
```

The compiler plugin turns `key(person.id) { … }` into a group the runtime's code calls a movable group: its key combines the position of the `key` call in your source with the value you passed. The runtime's own comment says it lets "the state and nodes generated by a loop to move with the composition implied by the key". So on the next run, Ben's call finds the group marked with Ben's id wherever it now sits, and moves it, slots and nodes, to its new place. Zoe's call finds no group with her id and gets a new one.

The value only has to be unique among the calls inside that loop, not across the app: "it needs to only be unique amongst the invocations of composables at the call site". Two people with the same id would share an identity, and their remembered values could cross over again.

`LazyColumn` takes the same idea as a parameter: `items(people, key = { it.id }) { PersonRow(it) }`.

## Go deeper: What if the list is only ever appended to?

- A chat screen only ever adds messages at the bottom, and never inserts, removes or reorders. Does each message row need key()?::Not for correctness. Appending leaves every old row at its position, so every call finds its own group by order; only the new row gets a new group. The docs say this too: with an item added at the bottom, "Compose can reuse the instances already in the Composition since their location in the list haven't changed". Insert, remove or reorder even once, and the rows below that point shift; that's when key() matters.

## The analogy

The prompt book again. A crowd scene has ten extras, and the book only says "extra 1 wears the red scarf, extra 2 the hat". One night a new extra joins at the front of the line. The stage manager hands out costumes by place in line, so the newcomer gets the red scarf, and every extra ends up in the costume of the one before. Pin a name tag on each costume (key()), and every extra gets their own, wherever they stand.

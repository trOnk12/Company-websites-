1. The first run builds the composition: a tree of groups, nested the way the calls nest. The if on showError has a group too, empty while showError is false.

  2. Button also leaves a node: a real UI element the screen is made of. Counter leaves only its group.

  3. Groups keep values in slots: the arguments they got last time, and what they asked to remember, like Counter's count.

  4. The runtime stores it all in call order in one slot table: each group with its key, then its slots. Counter's key (here a made-up 93) comes from its name and parameters.

  5. showError becomes true and the calls run again. A reader walks the table from the start, in step with the calls. Predict: does Counter keep its 0?

  6. Yes. ErrorBanner goes inside the if's group, so the next group is still Counter's: key 93 matches, and the 0 comes with it.

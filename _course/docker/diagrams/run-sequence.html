1. The docker command does no container work itself. It sends the request to dockerd, the Docker daemon: a program that keeps running in the background and does the work for every docker command.

  2. dockerd hands the container's life, create, start, stop, to containerd, a second long-running program.

  3. For each container, containerd starts a small helper process, a shim (here containerd-shim-runc-v2), which will stay with the container.

  4. The shim runs runc, create then start, with the container's config.json: which program, which root filesystem, which namespaces, which limits.

  5. runc asks the kernel for new namespaces and a cgroup with the limits, then starts sleep in them, with two system calls: clone makes the process, exec loads the program. Predict: runc's job is done. Who is sleep's parent now?

  6. runc exits. sleep, PID 1363, is left as the child of the shim, PID 1337. What runs now is what puzzles 0 to 7 found: one process, in namespaces, in a cgroup.

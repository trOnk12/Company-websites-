1. When HotSpot sets up Counter, it builds its method table: numbered slots, one per method a subclass could override. next gets slot k and points to Counter's code, v + 1.

  2. Setting up Loud, HotSpot first copies Counter's table: same slots, same order, slot k still pointing to v + 1.

  3. Loud overrides next, so HotSpot replaces slot k in the copy: it now points to v + 10. The slot number doesn't change.

  4. use(c) runs invokevirtual Counter.next, and c holds a Loud. Predict: which slot is read, and which code runs?

  5. The object leads to its class, Loud, and the call reads slot k of Loud's table: v + 10. One lookup, no search through parent classes.

  6. A final method that overrides nothing gets no slot at all: HotSpot can call it directly. The caller's bytecode still says invokevirtual.

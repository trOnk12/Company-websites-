1. The UI toolkit isn't thread-safe, so everything UI-related happens on one thread, in order. That thread runs an endless loop (the Looper): take the next message from the MessageQueue, run it fully, repeat. Touches, frames and your own posted code are all messages.

  2. Remember the Binder thread from puzzle 5? When system_server says "resume your screen", the message arrives on a Binder thread, which drops it into the main queue with a Handler.

  3. The clerk takes the first message and handles it completely before looking at the next one. That's why you never need locks for your views.

  4. Now one message is slow: code on the main thread sleeps, reads a big file, or waits on the network. Everything behind it waits too, including the user's touch.

  5. If a touch isn't handled within 5 seconds, Android shows the ANR dialog: Application Not Responding. Long before that, every 16 ms frame that can't be drawn is a dropped frame: jank.

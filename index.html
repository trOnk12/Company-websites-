Driftless: where was the taxi, really?

A side project: a Kotlin library that estimates where a vehicle is between GPS fixes that arrive rarely, late or out of order. The core is a pure function from events to state, so every run can be replayed. The time a fix was measured and the time it arrived are kept apart, so a late fix can’t move a vehicle backwards. On top sits an online map matcher (a hidden Markov model over road segments).

I tested it on 200 real Porto taxi trips, keeping one fix a minute and scoring the guesses against the points I hid. Median error, on points where every road-based method found a route:

WhereNo map (Kalman filter)Following the roadsPoints
Turns69 m38 m168
Straight roads39 m35 m471

So following the roads roughly halves the error on turns and barely helps on straight roads, where the worst 5% of guesses actually got worse (99 m to 110 m). My own report calls the edge over simpler road-snapping methods small but real, and path-following inconclusive. That is the result, so that is what it says here.

Tested with property-based tests, real-socket end-to-end tests and a reproducible benchmark. The repository is private; I’m happy to walk you through it. Data: ECML/PKDD 2015 Porto taxi trips (CC BY 4.0) and OpenStreetMap (ODbL).

How I use AI, and how I check it

Most of my Android work predates these tools. At Arrive I use AI every day: to read documentation, to build features, and to write the iOS and Node parts of my work.

It fails in predictable ways. It sometimes gets the definition of done wrong, and where the context doesn’t have the answer, it fills the gap with something plausible. And a passing test, AI-written or not, doesn’t prove that it checks anything. So:

  • Spec first. We collect the specs and documents and give the model all of it, so it has less to invent.
  • I read every line before it goes up for review, and iOS changes go through iOS engineers.
  • Tests get tested. I run mutation testing on AI-written tests: the tool plants small bugs, and a test that still passes is missing an assertion.
  • Rules, not examples. Property-based tests check what must hold for any input, not just the three cases someone thought of.
